# Архитектура «ФСП Карьера»

Документ описывает, как устроено решение, какие решения приняты и почему, и что остаётся путём
развития. Основа: ТЗ специального трека и уточнения организаторов. Сверка требований с кодом
находится в `docs/compliance.md`.

Принцип: всё, что даёт баллы по критериям 1-2 (тестирование и подбор, 60%), работает без внешних
ключей и без GPU. LLM и внешние сервисы допустимы только как улучшения поверх детерминированного
ядра, с запасным вариантом без них. Сейчас ни LLM, ни эмбеддинги в коде не используются.
Нереализованное помечено как путь развития или концепция.

## 1. Компоненты

```
                    ┌──────────── gateway (nginx) ─────────────┐
браузер ──────────► │ /        → frontend (React SPA)          │
                    │ /api /docs /admin → backend (FastAPI)    │
                    │ /auth    → keycloak (realm fsp + fsp-id) │
                    │ /mail    → mailpit                       │
                    └──────────────────────────────────────────┘
backend ──HTTP──► scoring (FastAPI, без состояния: банк заданий, IRT, ранжирование)
backend ──SQL───► postgres 17 (образ с pgvector, задел под эмбеддинги)
backend ──OIDC──► keycloak
backend ──SMTP──► mailpit
(путь развития) backend ──HTTPS─► LLM-провайдер РФ (GigaChat / YandexGPT), с запасным вариантом
```

| Сервис | Ответственность | Почему отдельно |
|---|---|---|
| `backend` | Бизнес-логика, данные, права, OpenAPI | Модульный монолит: одна транзакция на сценарий, один источник правды |
| `scoring` | Чистые вычисления: банк семейств, сборка теста, оценка θ по IRT, скор подбора с вкладами | Те же функции вызывают и backend, и скрипты валидации, поэтому отчёт валидации измеряет код, который работает на стенде. Будущие тяжёлые зависимости (модель эмбеддингов) не попадут в backend |
| `keycloak` | Вход, регистрация, подтверждение email; mock-реалм `fsp-id` в роли ФСП ID | ФСП ID работает на Keycloak (ТЗ). Переход на их стенд меняет настройки `FSP_ID_*`, а не код |
| `postgres` | Данные приложения и Keycloak в отдельных базах. Образ с pgvector: эмбеддинги можно хранить здесь без отдельного Qdrant или Elastic | Меньше памяти, проще запуск |
| `mailpit` | Перехватывает письма Keycloak и backend (подтверждение email, новое приглашение) | Демонстрация без настоящей почты |

Что сознательно не добавлено, пока нет потребности: Redis, очереди и воркеры (истечение приглашений
считается при чтении по `expires_at`), S3 (файлы лежат в volume через `LocalFileStorage`, интерфейс
для замены уже есть), песочница для исполнения кода (организаторы её не требуют), outbox и вебхуки
(описаны в концепции ATS), дробление на микросервисы сверх `scoring`.

Ресурсы: решение укладывается в сервер проверки (32-64 ГБ RAM, около 8 CPU, без GPU), моделей в
составе нет. Путь развития: CPU-эмбеддер (`sergeyzh/rubert-mini-frida`, 312-мерные векторы)
отдельным фактором скора, если валидация подбора покажет прирост.

## 2. Слои backend

```
app/api/<module>.py            роутеры: только HTTP, права через *UserDep
app/schemas/<module>.py        Pydantic-схемы ввода и вывода (конструкторы from_…)
app/services/<module>.py       бизнес-логика, DI через Annotated[..., Depends()]
app/services/db/models/<m>.py  модели SQLAlchemy; enum как varchar + CHECK (str_enum_column_type)
migrations/versions/           Alembic; справочники и демо-данные через сид-миграции или команду
```

Правила, которые соблюдаются во всех модулях:

- `operationId` совпадает с именем функции ручки, из него orval генерирует хуки фронта. Имена ручек
  уникальны.
- Данные кандидата уходят работодателю только через `CandidateEmployerView`, единственную
  схему-шлюз. Контакты открываются только через раскрытие (§5.2).
- Связи моделей объявлены с `lazy="raise"`, поэтому скрытых N+1 запросов нет.
- Ограничения целостности заданы в БД (CHECK, UNIQUE, FK), а не только в коде.
- Каждая ручка перечисляет свои ошибки в OpenAPI: `responses=error_responses(...)` (`app/errors.py`)
  с ошибками зависимостей (`ROLE_ERRORS`, `COMPANY_MEMBER_ERRORS`) и бизнес-ошибками сервиса.
  Тело ошибки `ErrorRead {error, detail}`, где `error` это имя класса ошибки, по нему ветвится фронт.

## 3. Тестирование и категоризация (критерий 25%)

### 3.1. Путь кандидата

```
регистрация (Keycloak, email) → согласие на обработку → профиль (форма или черновик из PDF-резюме, §6)
→ опрос: направление (специализация)
→ самостоятельный выбор заявленного грейда   (обязательно по ТЗ)
→ тест на заявленный грейд → категория «специализация × подтверждённый грейд»
```

«Отрасль» в ТЗ означает ИТ-направление (backend, frontend, ML и т. д.), а не индустрию, это
подтвердили организаторы. Эту роль играет справочник `specializations`, а `industries` относится
только к компаниям.

### 3.2. Банк: семейства заданий против утечки

Единый набор заданий утекает, а LLM-генерация для каждого кандидата делает сложность несопоставимой.
Поэтому банк состоит из параметризованных семейств (`scoring/app/services/assessment/bank/`):

- Семейство это генератор экземпляра по seed, эталонный ответ, параметры IRT (`a`, `b`) и
  компетенция. Сейчас в банке 78 семейств по 9 компетенциям: Python, SQL, алгоритмы, HTTP/API,
  JavaScript, веб, React, ML, статистика. На каждую компетенцию есть по два сложных семейства для
  Senior и Lead (b около 1.9 и 2.3): рекурсивный CTE и рамка окна, Дейкстра и рюкзак с ловушкой
  жадного решения, порядок `async/await`, CSP и SameSite-cookie, порядок эффектов и перерисовки по
  контексту в React, token bucket и свежесть кеша, ROC AUC и порог по стоимости ошибок, взвешенная
  конверсия и поправки на множественные сравнения.
- Экземпляр детерминирован: `Random(f"{seed}:{family_id}")`, seed берётся из id попытки. Данные,
  имена, сценарии и порядок вариантов у экземпляров разные, а структура решения и сложность общие
  для семейства.
- Эталоны не пишутся руками, а вычисляются: Python-фрагменты исполняются, SQL выполняется в SQLite,
  алгоритмические задачи решаются кодом (BFS, Дейкстра, ДП). Ответы JS-семейств считает модель
  семантики, в тестах они сверяются с настоящим Node.js на 15 seed каждое. Правила без внешнего
  эталона (CSP, cookie, React, кеш, token bucket, поправки) проверены на разобранных вручную случаях
  (`scoring/tests/test_bank_rules.py`).
- Инвариант в тестах: у двух экземпляров одного семейства ответ совпадает меньше чем в 50% случаев
  (`test_leaked_answer_rarely_fits_another_instance`). Иначе утёкший экземпляр работал бы как
  шпаргалка.
- Эталоны хранятся в backend (`attempt_items.answer`) и никогда не уходят на клиент, ни во время
  теста, ни после. Кандидат видит только итог по компетенциям.
- LLM во время теста не участвует. Путь развития: российская LLM как офлайн-источник черновиков
  новых семейств с ручной проверкой.
- Форматы заданий не требуют исполнения кода кандидата: «что выведет код», короткий численный ответ,
  ситуационный выбор с пулом сценариев.

### 3.3. Сборка и оценка

- LOFT по спецификации (`assembly.py`): 15 заданий за 25 минут, квоты по компетенциям направления
  (backend: Python 4, SQL 4, алгоритмы 4, HTTP 3; frontend: JS 6, веб 3, React 3, HTTP 3;
  data-science: Python 3, ML 4, статистика 4, SQL 4). Внутри квоты задания выбираются случайно из
  окна ближайших по сложности к целевой (порог грейда + 0.2). Семейства двух последних попыток
  исключаются, пока хватает других.
- 2PL IRT, θ и SE оцениваются методом EAP с априорным N(0, 1.25²) на сетке (`irt.py`, стандартная
  библиотека, без numpy). С N(0, 1) оценка стягивалась к нулю у верхних грейдов, и честного Lead
  тест подтверждал примерно в 40% попыток.
- Грейд G подтверждён, если `θ − 0.25·SE ≥ c_G`. Пороги: Junior −1.0, Middle 0.0, Senior 1.0,
  Lead 1.8; стажёр подтверждается всегда.
- Продление у порога. Если порог ближе одной SE к оценке (`|θ̂ − c_G| < SE`), решение близко к
  случайному, и попытка получает ещё 5 заданий со сложностью у порога (в экспресс-тесте 3), не
  больше двух раз. Время на них добавляется в темпе основного теста. Это укороченный
  последовательный классификационный тест (правило доверительного интервала, Kingsbury & Weiss):
  уверенные случаи заканчиваются на 15 заданиях, пограничные добирают информацию там, где она нужна.
  Решение о продлении принимает scoring (`extension_size`, поле `extend_items` в ответе
  `/assessment/score`), backend добавляет задания (`/assessment/extend`) и сдвигает дедлайн. По
  валидации в среднем выходит 18.8 задания, максимум 25; без продления стабильность ниже примерно на
  9 п. п.
- Устойчивость решения (`retest_agreement`) это вероятность, что повторная попытка на тот же грейд
  даст то же решение, по апостериорному прогнозу θ ~ N(θ̂, 2·SE²). Кандидат видит её в результате;
  ниже 65% результат помечается «у границы грейда». Так нестабильность у порога объясняется
  кандидату, а не выглядит как случайно меняющийся грейд.
- Длина 15 и K = 0.25 подобраны валидацией (`docs/validation-assessment.md`). При K = 0.5 слишком
  много честных кандидатов не подтверждается, при K = 0 завышение доходит до 15-25%. Недооценка
  обходится дешевле завышения: кандидату сразу предлагается тест на грейд ниже, а профиль не
  скрывается.
- Сознательно не сделано накопление ответов между попытками: по симуляции оно дало бы 83-88%
  стабильности, но повторная попытка перестала бы быть независимой, а на новом аккаунте проверяющего
  не работало бы вовсе. Полноценный CAT с GLR по симуляции добавляет 1-3 п. п. поверх продления,
  а банк заданий у порога быстро кончается.

### 3.4. Правила грейда

Правила собраны в одной чистой функции `evaluate_option` (`backend/app/services/assessment.py`) и
покрыты тестами.

| Ситуация | Правило |
|---|---|
| Прошёл тест на G | Грейд G подтверждён, кандидат попадает в категорию |
| Не прошёл на G | Грейд не понижается принудительно. Тест на G−1 предлагается сразу, без 7-дневного ожидания, если G−1 выше уже подтверждённого |
| Уверенно прошёл (`θ − K·SE ≥ c_{G+1}`) | Сразу предлагается тест на G+1 |
| Смена подтверждённого грейда или направления | Не чаще раза в 90 дней |
| Повтор неудачной попытки на тот же грейд | Через 30 дней; семейства прошлых попыток исключены |
| Нет пройденного теста | Кандидат виден работодателю с пометкой «грейд не подтверждён» и стоит ниже в ранжировании |
| Время вышло | Попытка завершается при следующем обращении, неотвеченные задания считаются неверными |
| Двойной старт | Запрещён частичным уникальным индексом в БД |

Данные: `candidate_grades` (категория: направление, заявленный и подтверждённый грейд, θ,
предложение следующего теста), `assessment_attempts`, `attempt_items`. API:
`/api/v1/candidate/assessment/*`.

### 3.5. Защита от списывания

Обязательна только устойчивость к утечке (§3.2). Дополнительно есть лимит времени на попытку, а
условие, код и варианты ответа на странице теста нельзя выделить и скопировать. Это барьер против
копирования задания в чат-бот одним движением, а не защита: скриншот и devtools остаются.

Детектор утечки. Неверный ответ на текстовое задание, который совпал с эталоном чужого экземпляра
того же семейства, почти наверняка списан: случайно получить такой ответ трудно. При оценке backend
передаёт в `scoring` эталоны этого семейства из попыток других кандидатов (до 200 на семейство), и
`matches_foreign` (`scoring/app/services/assessment/assembly.py`) сверяет их той же функцией
`is_correct`, что и основной ответ. Совпадение с эталоном, равным собственному, утечкой не считается.
Результат хранится в `assessment_attempts.foreign_answers`, его видно в админке и в карточке
кандидата у работодателя (по попытке, подтвердившей грейд).

На грейд детектор не влияет: такой ответ и так неверный, а механика семейств уже обесценила
утечку. Детектор только показывает сам факт. Валидация (`docs/validation-assessment.md`, раздел
«Устойчивость к утечке»): при доле утёкших ответов 25% помечены 71-76% кандидатов, при 50% помечены
93-95%, среди честных 0%. Ограничение: в симуляции неверный ответ честного кандидата никогда не
совпадает с чужим эталоном, а в жизни случайные совпадения возможны, особенно у числовых ответов.
Поэтому пометка служит сигналом для человека, а не санкцией.

Путь развития: журнал событий `visibilitychange` и `paste`, флаг «аномально быстро и верно».
Прокторинг остаётся в концепции.

## 4. ФСП ID и достижения

### 4.1. Привязка

- Основной вход на платформу идёт по email в realm `fsp`. ФСП ID это отдельный OIDC-провайдер, к
  которому кандидат привязывает профиль. Кандидат нажимает «Привязать ФСП ID» и входит в ФСП ID
  (Authorization Code + PKCE), бэкенд проверяет ID-токен (подпись, издатель, nonce) и берёт номер
  участника из claim `fsp_id`, а если его нет, то `sub` аккаунта ФСП ID
  (`backend/app/services/fsp.py`). Номера участника в токене настоящего ФСП ID может не быть.
  Используется тот же проверенный OIDC-клиент, что и для входа на платформу.
- На стенде ФСП ID работает как mock-реалм `fsp-id` в нашем Keycloak
  (`infra/keycloak/realm-fsp-id.json`): тестовые спортсмены athlete1-athlete4, пароль `fsp-demo`.
  Номер участника хранится атрибутом профиля, маппер кладёт его в ID-токен.
- Переход на настоящий ФСП ID меняет только настройки: `FSP_ID_PUBLIC_URL`, `FSP_ID_INTERNAL_URL`,
  `FSP_ID_REALM`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET`. Если вход через ФСП ID станет
  обязательным, он подключается в realm `fsp` как Identity Provider без изменений бэкенда.
- Один ФСП ID привязывается к одному профилю (уникальный индекс). Автоматической привязки по
  совпадению email нет.

### 4.2. Реестр

Модель реестра предложена нами, организаторы её одобрили.

- `FspEvent{title, discipline, starts_on, ekp_number}`. Номер в Едином календарном плане Минспорта
  позволяет работодателю сверить соревнование с официальным календарём; в демо-данных номера
  синтетические.
- `FspResult{fsp_id, event, award: winner|prize|finalist|participant, place, team_name}`.
- `FspAthleteRank{fsp_id, rank: III-I разряд|КМС|МС, assigned_on}`: спортивный разряд или звание
  по ЕВСК.

Дисциплины соответствуют пяти официальным дисциплинам вида спорта. Соревнования в демо-данных
повторяют календарь fsp-russia.ru: Чемпионат России, Кубок России, Кубок Федерации (отбор и финал),
Чемпионат и Первенство федерального округа, международные «Лидеры цифровой трансформации» (сам
хакатон ЛЦТ является соревнованием ФСП по продуктовому программированию). На стенде реестр хранится
в таблицах с демо-данными (`app.demo_seed`). Для реальной интеграции меняются только функции
`registry_results` и `registry_rank` (`app/services/fsp.py`): вместо таблиц они будут обращаться к
API ФСП.

### 4.3. Как достижения влияют на выдачу

- Достижения влияют только на ранжирование внутри категории, но не на грейд.
- Бонус = 1 − exp(−Σ вес·затухание). Победа и призовое место весят 1, финал 0.5, участие 0 (иначе
  профиль можно было бы набить онлайн-отборами). Все соревнования весят одинаково, результат
  двухлетней давности весит в e раз меньше свежего. Одна свежая победа даёт около 0.63, две около
  0.86.
- В подборке есть фильтр «есть достижения ФСП» и строка объяснения вида «Достижения ФСП: 2 (победы,
  призовые места, финалы), из них по профильной дисциплине: 1». Профильность задаёт
  `DISCIPLINE_SPECIALIZATIONS` (`app/services/fsp.py`): информационная безопасность соответствует
  направлению «Информационная безопасность», робототехника и БАС направлению Embedded,
  алгоритмическое программирование направлениям backend, data, gamedev и embedded, продуктовое всем
  программным направлениям. Профильность показывается только в объяснении, веса всех соревнований
  остаются равными. В карточке кандидата результаты помечены «проверено в реестре ФСП», рядом
  указан разряд или звание.
- Разряд на скор не влияет: его присваивают по тем же результатам, которые уже дают бонус, и
  результат считался бы дважды. Работодателю разряд понятен без расшифровки («КМС по спортивному
  программированию»), поэтому он показывается в карточке, PDF и профиле кандидата.
- Если истории ФСП нет, бонус равен 0, штрафа нет и в объяснении ФСП не упоминается; в карточке
  нейтральный текст. Это закреплено тестами (`backend/tests/test_fsp_standing.py`,
  `scoring/tests/test_matching.py`).

### 4.4. Что ещё можно взять из реестра ФСП (концепция)

По сайту и календарю ФСП (fsp-russia.ru): у ФСП 89 региональных представительств, соревнования
проходят как «Чемпионат и Первенство» (Чемпионат для 16+, Первенство для 14-18 лет), а сборная
России формируется по результатам. Для реальной интеграции предлагаем получать по ФСП ID:

- возрастную группу результата (Чемпионат или Первенство). Результаты Первенства полезны для
  стажировок и для концепции работы с несовершеннолетними (§9.2);
- членство в сборной и судейскую категорию как отдельные проверенные строки профиля, без влияния на
  скор;
- уровень соревнования (федеральный округ, всероссийское, международное) только для отображения:
  все соревнования по-прежнему весят одинаково.

### 4.5. Подсказка грейда по ФСП

Подсказать грейд по достижениям ФСП можно, но выбирает его сам кандидат. Чистая функция
`suggest_grade` рядом с `evaluate_option` (`backend/app/services/assessment.py`) смотрит результаты
за два года: победа и ещё одна победа или призовое место дают Senior, одно призовое место Middle,
только финалы Junior. Это эвристика до калибровки на реальных данных. Без истории ФСП подсказки нет,
и ФСП в выборе грейда не упоминается. На подтверждение грейда подсказка не влияет, его даёт только
тест. Тесты: `backend/tests/test_assessment_rules.py`.

## 5. Подбор и выход на контакт (критерий 35%)

### 5.1. От потребности работодателя к подборке

`HiringNeed` (`backend/app/services/hiring.py`) описывает направление, грейд, обязательные и
желательные навыки из справочника, форматы работы, город, вилку зарплаты в рублях (обязательна,
CHECK в БД) и то, чем занимается команда. Подборка строится так:

1. Пул: опубликованные профили нужного направления (есть действующее согласие на показ), грейд
   запрошенный или соседний. Кандидаты без подтверждённого грейда и даже без категории остаются в
   пуле.
2. Скор (`scoring/app/services/matching.py`, без состояния, возвращает вклад каждого фактора):

```
Match = 0.40·Навыки + 0.30·Грейд + 0.10·Сила профиля + 0.10·ФСП + 0.10·Формат/город
  Навыки        покрытие обязательных (вес 2) и желательных (вес 1) навыков
  Грейд         вероятность, что истинный уровень кандидата совпадает с запрошенным (соседний ×0.4):
                априорно заявленный грейд верен в 60% случаев и завышен на ступень в 30%;
                результат любой попытки теста (θ̂ ± SE, пройденной или нет) уточняет это по Байесу
  Сила профиля  запас θ над порогом подтверждённого грейда; только внутри запрошенной категории
  ФСП           бонус за результаты (модуль fsp); без истории 0, без штрафа
```

3. Порядок: сначала кандидаты, совместимые по вилке, затем по формату работы (это условия
   кандидата, а не пожелания), внутри групп по скору. Несовместимые кандидаты не скрываются, а уходят
   вниз с явной причиной.
4. Объяснение строится детерминированно из вкладов, без LLM: «Обязательные навыки: 1 из 2 (нет
   PostgreSQL)», «Грейд Middle подтверждён тестом», «По тесту уровень соответствует запрошенному с
   вероятностью 94%», «Подтверждено тестом 1 из 3 навыков потребности: Python», «Кандидат в другом
   городе», «Верх вилки ниже ожиданий кандидата». Каждый навык потребности показан с пометкой
   «подтверждён тестом», «заявлен» или «нет». Заявленный навык считается подтверждённым, если в
   попытке, подтвердившей грейд, по его компетенции верно не меньше 50% ответов и заданий было не
   меньше двух (`COMPETENCY_SKILLS`, `verified_skill_slugs` в `hiring.py`). Компетенции без навыка в
   справочнике (http_api, web, ml, stats) подтверждают только грейд. На скор пометка не влияет: вес
   имеет смысл менять, только если валидация покажет выигрыш. В карточке кандидата вклады показаны
   полосками с весами.
5. Уточнение без потери подборки. Фильтры (грейд, навыки, формат, «только подтверждённые») сужают
   выдачу, не меняя порядка, и хранятся в адресе страницы, поэтому к выдаче можно вернуться и
   поделиться ссылкой. Кандидатов можно отобрать в шортлист потребности (`shortlist_entries`): он
   показывается над выдачей при любых фильтрах, а кандидат, скрывший профиль, из него выпадает.
6. Поиск по банку кандидатов работает тем же конвейером без потребности: ранжирование по силе
   профиля и ФСП.
7. Обзор категорий (`GET /employer/categories`, `HiringService.categories`) одним агрегирующим
   запросом считает, сколько опубликованных кандидатов в каждой категории «направление × грейд» и
   сколько из них подтвердили грейд. Категория определяется так же, как в пуле выдачи. В банке
   кандидатов это сетка по направлениям, у потребности её грейд и соседние («рекомендованные
   категории», ТЗ §2.1); клик по категории ставит фильтр.

Почему скор устроен именно так, показывает валидация (`docs/validation-matching.md`,
`scoring/validation/matching.py`). Потребности и кандидаты синтетические, с известной «истинной»
релевантностью; резюме зашумлены лишними навыками, часть кандидатов завышает грейд. Первая версия
скора (сила профиля с весом 0.30 для всех, формат как мягкий вклад) проигрывала подбору без теста.
Валидация это показала, и скор переделали: байесовское соответствие грейду, сила профиля только
внутри категории, формат как условие. Результат: P@5 0.68-0.70 против 0.38-0.41 у поиска по
ключевым словам резюме, 0.31 у BM25 по тексту резюме, 0.34-0.51 у сортировки только по заявленному
грейду и 0.14 у случайного порядка (это доля релевантных в пуле); nDCG@10 0.84-0.87 с 95%
бутстреп-интервалом ±0.05-0.06 по потребностям. Тест повышает качество тем сильнее, чем чаще
кандидаты завышают грейд: при 50% завышающих nDCG@10 0.840 против 0.780 без теста. Если все
оценивают себя честно, разница в пределах шума (0.867 против 0.858).

Слепой генератор убирает преимущество, заложенное построением данных. Навыки в резюме записаны
названием, синонимом из словаря или перефразом вне словаря («питон», «Postgres 16»), 30%
кандидатов набивают резюме ключевыми словами, а релевантность считается по скрытым истинным
навыкам. Подбор проседает (P@5 0.50, nDCG@10 0.74), но остаётся заметно выше бейзлайнов
(ключевые слова 0.27 / 0.39, BM25 0.20 / 0.28, только грейд 0.32 / 0.49): тест и байесовская
модель грейда не зависят от того, как кандидат описал навыки. Fairness: кандидатов без ФСП в пуле
59-61%, в топ-10 полного подбора 50-52%. Это верхняя оценка перекоса, потому что в генераторе ФСП
не связан с релевантностью.

### 5.2. Приглашение-оффер

`Invitation` (`backend/app/services/invitations.py`) хранит компанию, кандидата, отправителя,
потребность (необязательна), должность, описание предложения, вилку (обязательна, CHECK), способ
связи, статус, причину отказа и отметки времени.

```
SENT ──(кандидат открыл раздел)──► VIEWED ──► ACCEPTED ──► контакты раскрыты, переписка открыта
  │                                  ├──────► DECLINED (зарплата / стек / формат / не ищу / другое)
  ├──(работодатель отозвал)──────────► WITHDRAWN
  └──(7 дней без ответа)─────────────► EXPIRED   (считается при обращении, без фоновых задач)
```

Все правила проверяются на бэкенде:

- Скрытый порог. Ожидания кандидата по зарплате работодателю не видны. Приглашение, у которого
  верх вилки ниже ожиданий, не отправляется (409), а подборка заранее помечает таких кандидатов
  «вилка ниже ожиданий».
- Защита от спама. От компании кандидату может ждать ответа только одно приглашение (частичный
  уникальный индекс). Одновременно ждут ответа не больше 5 приглашений новой компании и 20 у
  компании с подтверждённым доменом (§5.6), любой ответ освобождает место. После отказа компания
  30 дней не может снова пригласить того же кандидата (409).
- Поэтапное раскрытие. До принятия работодатель видит «Кандидат №1174» без ФИО, контактов, названий
  компаний и названий команд ФСП (команда вместе с соревнованием выдаёт человека). После принятия
  ФИО, email, телефон, Telegram, компании в опыте и команды ФСП видит только пригласившая компания
  (`ContactReveal`). Кандидат может закрыть доступ в любой момент.
- Контакты в свободном тексте («о себе», опыт, образование, свои навыки, город) до раскрытия
  заменяются на «[контакт скрыт]» (`mask_contacts`), иначе правило обходилось бы одной строкой
  «пишите в tg: …». Это эвристика на регулярных выражениях, кандидат видит результат в предпросмотре.
- Переписка после принятия доступна кандидату и сотрудникам компании в разделе «Сообщения»
  (`/messages`, `GET /chats`): слева список переписок с последним сообщением и счётчиком
  непрочитанных, справа открытая переписка. Обновление опросом без WebSocket: открытая переписка
  опрашивается раз в 3 секунды, пока вкладка видна. Сторон две: кандидат и компания как общий ящик
  (`invitations.candidate_read_message_id` / `company_read_message_id`). Если прочитал любой
  сотрудник, для компании сообщение прочитано, а сообщение коллеги показывается как своё. Открытие
  переписки отмечает её прочитанной. После отзыва доступа к контактам переписка доступна только для
  чтения (409 `ChatClosedError`), потому что она тоже канал связи.
- Уведомления. `GET /notifications` возвращает счётчики того, что ждёт действия: непрочитанные
  сообщения, приглашения кандидату без ответа, отклики и встречные предложения для компании,
  принятые приглашения без первого сообщения компании. Запрос только читает данные, просроченное
  отсекается условием. Фронт опрашивает его раз в 10 секунд и в фоне: счётчики в шапке и на
  вкладках, «(N)» в заголовке вкладки браузера, всплывающее уведомление. При изменении счётчиков
  списки приглашений и переписок сразу перезагружаются.
- Письма. Кандидат получает письмо о новом приглашении, отправитель приглашения о принятии или
  отказе (с причиной). Контактов кандидата в письмах нет: после отзыва доступа копия осталась бы в
  почте.
- «Почему вам». Приглашение по потребности хранит снимок совпадения на момент отправки
  (`invitations.match_snapshot`): процент совпадения, навыки потребности с пометками «подтверждён
  тестом», «заявлен» или «нет в профиле», грейд и достижения ФСП (без истории ФСП они не
  упоминаются). Кандидат видит, за что его выбрали, в карточке приглашения и в письме. На обычных
  площадках такой обратной связи нет. Скрытых данных в снимке нет: ни ожиданий по зарплате, ни
  вкладов скора.
- Репутация работодателя считается по поведению, а не по анкете. В карточке приглашения кандидат
  видит, в какой доле принятых приглашений компания написала в течение 3 дней, через сколько она
  обычно пишет и какую долю приглашений отзывает. Показатели считаются при чтении из `invitations`
  и `invitation_messages` (два запроса на список) и показываются начиная с 5 завершённых
  приглашений, чтобы одна неудача не испортила репутацию новой компании. Это рабочая часть защиты
  от недобросовестных работодателей без модерации.
- Кейс в приглашении. Компания может приложить короткий вопрос о подходе к задаче (до 1500 знаков).
  Кандидат видит его сразу и при желании отвечает вместе с принятием (до 3000 знаков), а компания
  видит ответ уже вместе с контактами. Кейс показывает, как человек думает, и не должен быть
  бесплатной работой.
- Чужое приглашение неотличимо от несуществующего (404).

### 5.3. Демо-данные

`python -m app.demo_seed [N]` (в Docker: `docker compose exec backend python -m app.demo_seed`)
создаёт N демо-кандидатов, по умолчанию 90, около 30 на направление: при меньшем числе пул у
потребности песочницы слишком бедный. Кандидаты проходят тест через настоящий механизм, сборку в
scoring и сервис попыток, а ответы моделируются по 2PL от «истинного» уровня. Поэтому их грейды, θ
и итоги по компетенциям получены так же, как у живых людей. Демо-пользователи помечены
`keycloak_sub = demo:N`, войти под ними нельзя, повторный запуск пересоздаёт их. Сид также создаёт
компанию «Пример Технологии» с историей из 10 приглашений этим кандидатам (принятия с перепиской в
разные сроки, отказы, отзыв, истечение), на ней видна репутация работодателя.

Демо-режим для жюри (`DEMO_MODE=true`, `backend/app/services/demo.py`):
`POST /api/v1/demo/login {role}` создаёт пользователя-песочницу без Keycloak (`keycloak_sub` с
префиксом `jury:`, удаляется через сутки). Демо-работодатель получает компанию и готовую
потребность. Демо-кандидат получает опубликованный профиль, доступ к экспресс-тесту из 6 заданий и
приглашение от «Пример Технологии» (если сид запускали), поэтому сразу видны «почему вам», кейс и
репутация работодателя. Полный путь с регистрацией через Keycloak при этом тоже работает.

Песочницы не мешают проверке (`User.sees_sandboxes`, `published_candidates(sandboxes=...)`,
`_vacancy_query`):

- Зарегистрированные пользователи песочниц не видят: ни кандидатов в выдаче и категориях, ни
  вакансий в ленте, ни по прямому номеру. Иначе каждый демо-вход добавлял бы всем ещё одного
  «Демо Кандидата» и копию демо-вакансии.
- Песочницы видят друг друга, на этом построен сценарий «вторая роль в окне инкогнито». В выдаче и
  ленте они стоят после засеянных и настоящих кандидатов и вакансий.
- Общая демо-компания «Пример Технологии» приглашает каждую песочницу-кандидата, поэтому на неё не
  действует квота ожидающих приглашений и заморозка жалобами (§5.6).
- Тестовых спортсменов ФСП ID четыре, поэтому привязка, которую держит песочница, переходит к тому,
  кто привязывает этот ФСП ID следующим. Привязки настоящих пользователей не затрагиваются.

### 5.4. Регулярные задания: кейс недели

ТЗ просит регулярные короткие задания, которые поддерживают профиль актуальным и дают работодателю
свежий сигнал. Задания с известным ответом проверяет система, открытые проверяет работодатель.

- Кейс недели (`backend/app/services/cases.py`, `weekly_cases`). Раз в неделю кандидат получает одно
  задание своего направления со сложностью его грейда (подтверждённого, иначе заявленного). Это
  экземпляр семейства из банка (`scoring`: `weekly_case`, `/assessment/case`), поэтому эталон
  вычисляется, у каждого кандидата и недели свой экземпляр, а проверка та же, что в тесте. Кейс
  создаётся при первом обращении на неделе (уникальность «кандидат × неделя» в БД), без фоновых
  задач. Ответ даётся один раз, эталон не уходит на клиент ни до, ни после.
- На грейд кейс не влияет, грейд меняет только тест. Работодатель видит «кейсы недели: N за 30
  дней» в карточке и строку в объяснении подбора. Веса скора не меняются, пока валидация не покажет
  выигрыш.
- Открытые задания даёт работодатель через кейс в приглашении (§5.2): ответ кандидата приходит
  вместе с принятием и проверяется самим работодателем.

### 5.5. Встречное предложение

Вместо отказа «не устраивает зарплата» кандидат может ответить «готов при вилке от X»
(`POST /candidate/invitations/{id}/counter`). Это можно сделать один раз и только с суммой выше
верха вилки (`counter_block`, тесты `tests/test_counter_offer.py`). Контакты не раскрываются,
приглашение продолжает ждать ответа, сотрудник компании получает письмо. Компания одним действием
либо поднимает вилку до суммы кандидата (нижняя граница становится X, и приглашение возвращается
кандидату ещё на 7 дней), либо отзывает приглашение. Ожидания кандидата остаются скрытыми: сумму
называет только он сам.

### 5.6. Вакансии и отклик

Классический сценарий из ТЗ §3.3 дополняет основной, в котором приглашает работодатель.

- Вакансия это опубликованная потребность (`hiring_needs.published_at`, галочка в форме
  потребности). Лента кандидата (`GET /api/v1/candidate/vacancies`) показывает вакансии его
  направления (по категории, иначе по профилю) с процентом совпадения, посчитанным тем же скором,
  что в подборке работодателя, и пометками навыков «подтверждён тестом», «заявлен» или «нет».
- Отклик это приглашение с `direction = candidate`. У него общие статусы, истечение через 7 дней,
  переписка, `ContactReveal` и индекс «одно ожидающее на компанию × кандидата». Отклик сразу
  раскрывает контакты (ТЗ §2.2: «или откликнулся сам»), для него нужен опубликованный профиль.
  Компания отвечает «пригласить к разговору» (`accepted`, открывается переписка) или отказом с
  причиной. Пока ответа нет, кандидат может отозвать отклик и откликнуться снова.
- Правило отклика задаёт чистая функция `application_block` (`backend/app/services/invitations.py`).
  С подтверждённым грейдом можно откликаться на вакансии своего грейда ±1, без подтверждения не
  больше 3 откликов в неделю. Тест помогает выделиться, а не закрывает доступ, а лимит не даёт
  откликаться на всё подряд. Если откликнуться нельзя, лента показывает причину по тому же правилу,
  что проверяет ручка.
- Квота ожидающих приглашений, пауза после отказа и репутация компании считаются только по
  приглашениям компании, потому что отклики отзывает кандидат, а не она.
- Демо: вторая демо-компания «Северный Код» с пятью вакансиями разных направлений и грейдов.
  Вакансия работодателя-песочницы опубликована и сразу получает два отклика засеянных кандидатов
  через тот же `apply`.

### 5.7. Защита от фиктивных работодателей без модерации

ТЗ не требует проверять работодателей в MVP, поэтому защита встроена в механику, а не в ручную
модерацию (`backend/app/services/trust.py`):

- Уровень доверия `companies.trust_level`: 0 у новой компании, 1 после подтверждения домена. Квота
  ожидающих приглашений 5 и 20 соответственно (`pending_quota`): новая компания не сможет разослать
  спам, а ответ кандидата освобождает место.
- Подтверждение домена. Владелец вводит адрес в домене сайта компании, на него приходит подписанная
  ссылка (действует сутки, состояние в БД не хранится). Открыв её, владелец подтверждает доступ к
  ящику, домен сохраняется, и кандидат видит «домен … подтверждён» в приглашении и вакансии.
- Жалобы. Пожаловаться может только кандидат, которому компания писала, и только один раз на
  компанию («фиктивная вакансия», «просили деньги», «условия не те»). После 3 жалоб разных
  кандидатов компания замораживается: приглашать нельзя (409), её вакансии скрыты. Разбор и
  разморозка выполняются в `/admin` (раздел жалоб, поле `frozen_at`). Общие демо-компании стенда не
  замораживаются и не ограничены квотой (`is_shared_demo`), иначе один проверяющий, испытав жалобы,
  сломал бы демо следующему. Песочница работодателя замораживается как обычно.
- Путь развития: проверка ИНН и юрлица (DaData), уровень доверия 2 с большей квотой.

## 6. Регистрация, права, 152-ФЗ

- Регистрация по email с подтверждением: Keycloak `verifyEmail: true` и Mailpit.
- Роль выбирается один раз. Права проверяют `CandidateUserDep` / `EmployerUserDep` и проверка
  владения записью в сервисе.
- Согласия раздельные, с версией документа: `data_processing`, `profile_publication` и `fsp_data`
  (получение данных из реестра ФСП, то есть от третьего лица). Привязка ФСП ID требует `fsp_data` в
  начале и в конце входа, отзыв `fsp_data` отвязывает ФСП ID, отзыв `data_processing` снимает оба
  зависимых согласия, удаляет профиль и привязку.
- Пароли хранит только Keycloak, сессии хранятся как хеш токена в БД, cookie с флагами httpOnly и
  SameSite.
- Работа с несовершеннолетними вне MVP (для 14-18 лет нужно согласие родителей), подход описан в
  концепции (§9.2).

Приватность по разделам. До принятия приглашения кандидат может скрыть от работодателя «о себе»,
опыт, образование и софт-скиллы (`candidate_profiles.hidden_sections`, CHECK на известные значения,
`PUT /api/v1/candidate/profile/privacy`). Правило реализовано в единственной схеме, через которую
профиль уходит работодателю (`CandidateEmployerView.from_profile`): скрытые разделы пустые, а
`hidden_sections` сообщает работодателю, что откроется после принятия. Город, форматы и технологии
скрыть нельзя, по ним считается совместимость; стаж остаётся числом. Предпросмотр и PDF-профиль
следуют тому же правилу.

PDF-профиль (`backend/app/api/profile_pdf.py`, `GET /api/v1/candidate/profile/pdf`,
`GET /api/v1/employer/candidates/{number}/pdf`). PDF рендерится в слое API из схемы ответа
`EmployerCandidateRead`, той же, что у карточки кандидата у работодателя, поэтому правила
видимости наследуются, а не дублируются. До принятия приглашения это «Кандидат №N» с маской
контактов в тексте, без команд ФСП и названий компаний; после принятия добавляются ФИО, контакты,
команды и компании. Свой профиль кандидат получает в варианте «после принятия»
(`HiringService.own_details`, публикация не нужна). Содержимое: категория и дата подтверждения,
итоги теста по компетенциям, навыки, достижения ФСП с разрядом (без истории раздела нет), кейсы
недели, опыт, образование, «о себе». Используются reportlab (BSD) и шрифт DejaVu
(`fonts-dejavu-core` в образе).

Разбор PDF-резюме (`backend/app/services/resume.py`, `POST /api/v1/candidate/profile/resume`).
pdfplumber извлекает текст первых 5 страниц (файл до 5 МБ). Двухколоночная вёрстка делится по самому
широкому вертикальному просвету и читается по колонкам. Дальше работает чистая функция
`parse_resume` на правилах: контакты ищутся регулярными выражениями, навыки по названиям и
синонимам справочника (короткие «C», «Go» с учётом регистра), места работы по периодам в четырёх
форматах с поиском должности и компании в соседних строках (перенос периода в узкой колонке
склеивается). Стаж считается объединением периодов той же функцией, что в профиле, грейд и
направление определяются по словам в должностях. Ручка ничего не сохраняет: фронт заполняет пустые
поля формы, а кандидат проверяет и сохраняет. Для скана без текстового слоя возвращается 422 с
просьбой заполнить вручную (OCR не подключён). LLM не используется, поэтому персональные данные не
уходят наружу. Метрики на синтетике: `docs/validation-resume.md`.

## 7. LLM (путь развития)

Сейчас LLM не используется нигде: тест, подбор и объяснения работают на правилах. План:

- Только российские модели (GigaChat / YandexGPT) из-за требований к персональным данным.
- Интерфейс `LlmClient` с реализациями `GigaChatClient` и `NoopClient`, выбор через `.env`. Без
  ключа всё работает на правилах.
- Возможные применения: дополнение полей PDF-резюме, которые не нашли правила (структурированный
  JSON), перефразирование объяснений, офлайн-черновики семейств заданий.
- В документации будут перечислены модель, место вызова и данные, которые уходят провайдеру (без ФИО
  и контактов).

## 8. Валидация

Скрипты `scoring/validation/` вызывают те же функции, что и рабочий сервис. Подбор:
`docs/validation-matching.md` (§5.1). Тестирование:
`uv run python -m validation.assessment > ../docs/validation-assessment.md`.

Итоги по тестированию: r(θ̂, θ) ≈ 0.95. Стабильность при независимом повторе 77-78% (без стажёров,
чей грейд подтверждается всегда, 71-73%; до априорного N(0, 1.25²) и продления было 71-74% со
стажёрами). Честный Senior и Lead подтверждаются в 70-75% попыток (было 54-58% и 38-42%). Ложное
подтверждение грейда на ступень выше 7-14%. Утечка 100% ответов не повышает долю прошедших, тогда
как при едином наборе заданий проходят все.

Почему стабильность не 85%. Решение у самого порога близко к случайному при любом тесте:
стабильность там ≈ p² + (1−p)², и при |θ − порог| < 0.25 она составляет 49-56%, а при
|θ − порог| ≥ 0.5 уже 88-92%. Для 85% в среднем нужна SE около 0.2 у порога, а это 45-60 заданий.
Поэтому отчёт показывает стабильность по расстоянию до порога и индекс Руднера по одной попытке
(≈ 75%), а кандидат видит устойчивость своего результата. В реалистичной популяции θ ~ N(0, 1)
общая стабильность 77-78%. Чувствительность к разбросу сложности экземпляров внутри семейства (τ до
0.4) в пределах шума симуляции. Объём экземпляров внутри семейства однороден: коэффициент вариации
больше 0.3 только у 2 семейств из 53.

| Что | Как | Цель | Факт |
|---|---|---|---|
| Точность θ | 300 симулянтов на грейд, θ равномерно в диапазоне грейда, ответы по 2PL | r(θ̂,θ) ≥ 0.9 | 0.95 |
| Стабильность грейда (test-retest) | два прохождения с разными seed и семействами, с продлением у порога | совпадение ≥ 85% | 77-78% (без стажёров 71-73%); при \|θ − порог\| ≥ 0.5 88-92%, у самого порога около 50% |
| Устойчивость по одной попытке | индекс Руднера p² + (1−p)² | | ≈ 75% |
| Разделение грейдов | known-groups: симулянты всех грейдов | монотонный рост θ̂ | монотонно, от −1.4 до +2.1 |
| Устойчивость к утечке | кандидат знает долю L ответов: единый набор против семейств | P(завышения грейда) не растёт с L | 5-13% при любом L против 100% у единого набора |
| Подбор | 40 потребностей × 60 синтетических кандидатов с известной релевантностью | P@5/P@10 (доля релевантных в топе), nDCG@10 с бутстреп-ДИ, MRR, Recall@20 | P@5 0.68-0.70, nDCG@10 0.84-0.87; слепой генератор: P@5 0.50, nDCG@10 0.74 |
| Абляции | случайный порядок, только заявленный грейд, ключевые слова, BM25, без теста | полный подбор лучше бейзлайнов | лучше всех бейзлайнов; без теста лучше, если никто не завышает грейд (§5.1) |
| Fairness | доля кандидатов без ФСП в топ-10 | не обнуляется | 50-52% в топ-10 при 59-61% в пуле |

Эмбеддинги для навыков вне словаря проверены и не включены (`scoring/validation/embeddings.py`).
Модель `cointegrated/rubert-tiny2` сопоставляет перефраз навыка («питон», «датафреймы») с
ближайшим названием из словаря. На слепом генераторе nDCG@10 растёт с 0.74 до 0.80, формально
выше порога +0.02, но правильно сопоставлены только 26 из 40 перефразов. Ошибки идут с той же
близостью, что и верные ответы («докер» → torch 0.93, «гит» → torch 0.94, «джава» → golang 0.91),
порогом их не отсечь, и кандидат получил бы чужие навыки, что хуже пропуска. Верные случаи в
основном сводятся к вхождению названия («Python 3.12», «Redis Cluster»), которое разбор резюме уже
находит поиском по тексту, а в форме профиля навыки выбираются из подсказок словаря. Кроме того,
модель требует torch в рабочем образе. Путь развития: транслитерации как синонимы в словаре (правка
в `/admin`) и подсказка «возможно, вы имели в виду…» с подтверждением кандидатом.

Ограничение: все данные синтетические, экспертной разметки пар «потребность × кандидат» нет.
Основные таблицы строит генератор, который пишет навыки названиями из словаря матчера, поэтому их
цифры являются верхней границей. Слепой генератор (перефразы вне словаря, набивка ключевыми словами)
даёт более честную оценку.

Проверять решение вручную на своих профилях и проходить тесты самостоятельно можно через
демо-режим (§5.3) или полный путь с регистрацией.

### 9.1. Интеграция с ATS

Компании ведут найм в ATS (Хантфлоу, Talantix, Поток), и платформа должна передавать туда
кандидатов, а не становиться ещё одним окном.

- Реализована pull-лента событий без фоновых задач (`backend/app/services/ats.py`, карточка «API для
  ATS» в кабинете компании). Владелец выпускает API-токен: в БД хранится только хеш, как у
  ссылок-приглашений в компанию, токен показывается один раз и может быть отозван. ATS забирает
  события запросом `GET /api/v1/ats/events?since=<курсор>` с заголовком `Authorization: Bearer`:
  приглашение принято, отклонено или истекло, новый отклик, ответ компании на отклик, сообщение в
  переписке. События собираются из тех же записей, что видит кабинет. Курсор это время последнего
  события (`next_since`), у каждого события устойчивый id, чтобы ATS отбрасывала повторы. Данные
  кандидата (ФИО, контакты) передаются только при активном `ContactReveal`, по тому же правилу, что
  в кабинете.
- Следующий шаг (концепция): push-уведомления. Вебхуки пишутся в outbox-таблицу в той же
  транзакции, что и смена статуса, воркер отправляет их с повторами, запросы подписываются
  HMAC-SHA256. Адаптеры `AtsConnector`: Хантфлоу API v2 (создать кандидата, добавить на вакансию,
  этап «Источник: ФСП») и Talantix GraphQL (`createResponses`). Статус `accepted` соответствует этапу
  «Новый», `declined` отказу с причиной, идемпотентность обеспечивает `external_ref` = id
  приглашения.
- Ограничение: контакты, выгруженные в ATS, отзыв доступа уже не удалит, копия останется у
  компании. Поэтому интеграция включается только отдельным пунктом согласия на показ профиля, а
  кандидат видит, какие компании выгружают данные во внешние системы.

### 9.2. Несовершеннолетние (концепция)

Среди участников ФСП много школьников: почти каждое соревнование в календаре ФСП проходит как
«Чемпионат и Первенство», где Первенство это возрастная группа 14-18 лет. По 152-ФЗ обработка
данных лиц до 18 лет требует согласия законного представителя, а трудоустройство до 16 лет
отдельных условий. В MVP регистрация не спрашивает возраст. Предлагаемый подход: дата рождения при
регистрации; до 18 лет согласие родителя (подтверждение по email родителя той же подписанной
ссылкой, что у домена компании), профиль виден только компаниям с подтверждённым доменом,
приглашения только на стажировки; до 14 лет регистрация недоступна.

### 9.3. Опыт Triplebyte: приватность как часть продукта

Triplebyte (слепой тест вместо резюме, затем профиль, затем компании) в 2020 году сделал профили
публичными по умолчанию с неделей на отказ. После скандала решение отменили, но доверие кандидатов
было подорвано. В 2023 году Karat купил только продукт оценки, а сеть кандидатов закрылась. Ответы
на эту ошибку встроены в механику: профиль обезличен до принятия приглашения, контакты в тексте
маскируются, разделы можно скрыть, раскрытие можно отозвать, отклик является осознанным действием
кандидата, а публикация профиля требует отдельного согласия, которое по умолчанию не дано.
